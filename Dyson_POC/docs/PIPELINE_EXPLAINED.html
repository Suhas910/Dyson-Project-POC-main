01
DFX Design-Review · Internal briefing

Automated manufacturability review, straight from CAD

An engineer uploads a STEP file and chooses a process and material. The system measures the part, checks it against a 249-rule manufacturability catalogue, and returns a report that says what is wrong, where, and what to do about it.

Input STEP / STP Process read from geometry Catalogue 249 rules · 10 processes Typical run 50–90 seconds Output 3D model · dashboard · PDF Cost per part a fraction of a cent

The measurements are real geometry, not metadata: wall thickness is taken by casting rays into the solid, draft is computed against the direction the mould opens, and holes are found by analysing the surfaces themselves. Nothing depends on the CAD system that produced the file or on any annotation an engineer remembered to add.

03
The core idea

Two halves, with very different standing

If a stakeholder takes one thing from this briefing, it should be which half produced which number.

Computed

Geometry and verdicts

Measured from the model by a geometry kernel, then compared against numeric thresholds. Repeatable and auditable — the same file always gives the same answer.

  • Wall thickness, draft angle, hole size and depth
  • Undercut detection
  • Every compliant / non-compliant verdict
  • Which process families the part is checked against
  • Every feature name
  • Coverage accounting
Interpreted

Commentary and summary

Written by a language model that is handed the measurements and asked what they mean for manufacture. Advisory, and labelled as such wherever it appears.

  • Per-finding engineering commentary
  • The reading of which process the part is for
  • The part-level executive summary
  • Prioritised risks and recommendations
  • Nothing else

The model cannot change a verdict, and that is enforced by the data contract rather than by asking nicely. The JSON structure it must answer in has exactly three fields per finding — which finding, the comment, and a confidence — with unlisted fields rejected. There is nowhere to put a pass or a fail. A test sends a model response containing "status": "COMPLIANT" and asserts the finding is unchanged.

04
How it runs

Seven stages, each consuming the last

Stages 1–4 and 6–7 are computed. Stage 5 is the only place a language model decides anything, and even there it decides nothing — it writes.

1

Ingest

Computed step_loader.load_step()

Reads the file into a solid model, normalises it to millimetres, repairs minor topological damage, and records what it found — declared units, solid count, overall size, and whether the shape is genuinely a closed solid.

Why it matters Wall thickness assumes a closed solid. An open shell or a multi-body assembly still measures, but the numbers mean less — so the loader says so instead of letting the rest of the pipeline assume otherwise.
What runs
  • step_loader.py
  • load_step()
  • detect_declared_units()
  • ShapeFix_Shape — heal
  • BRepCheck_Analyzer — validate
→ LoadedPart · shape + units + warnings
2

Extract

Computed features.build_part_model()

Measures every face. It samples points proven to lie inside the trimmed surface, takes the outward normal, computes draft against the pull direction, casts rays inward for thickness, and groups cylindrical faces that belong to the same bore so a drilled hole is recognised as one feature. It then names every face from what it just measured — "Ø5.94 mm hole, upper front right", "R6.35 mm internal fillet", "Floor" — so a finding can say what it is about rather than quoting a face number.

Why it matters This is where the engineering lives. Three conventions are load-bearing — normal orientation, the draft convention, and sampling inside the trimmed face — and each is verified against parts whose true dimensions are known by construction. Names are derived from those same measurements and nothing else: a confidently wrong name sends an engineer to the wrong feature, which is worse than a number that tells them nothing.
What runs
  • features.py
  • interior_uv_samples()
  • outward_normal_at()
  • calculate_draft_angle()
  • measure_thickness_at()
  • group_cylindrical_faces()
  • is_face_occluded()
  • feature_naming.py
  • build_labels()
→ PartModel · one measured, named face record each
3

Classify

Computed process_classifier.classify()

Reads how the part was meant to be made. Scores each process family against the measurements — draft coverage, wall thickness and its spread, corner-radius consistency, gauge, solid count — and returns every family worth checking, with the sentences each score was computed from.

Why it matters Choosing the process by hand is the one step where a user can be silently, expensively wrong: pick machining for a moulded housing and every draft rule is skipped, and the report comes back clean. Reading it from the geometry removes that failure, and checking every candidate means a wrong reading costs a section nobody reads rather than a defect nobody sees.
What runs
  • process_classifier.py
  • measure_signals()
  • classify()
  • _Scorer.disqualify()
  • _Scorer.cap()
→ Classification · scored families + their evidence
4

Execute

Computed pipeline.execute_rules()

Runs the catalogue. Before any rule produces a verdict it passes three gates: is the metric computable, does the rule apply to the chosen material, and does it apply to this face. A rule that fails a gate returns one explained result rather than an indeterminate row per face.

Why it matters This is what separates a report from a data dump. Without material scoping, the ABS, PC and PP wall rules all fire at once and contradict each other. Without face scoping, hole rules run against flat walls.
What runs
  • pipeline.py · rule_scoping.py
  • execute_rules()
  • rule_material_applies()
  • metric_applies_to_face()
  • normalize_predicate()
  • _safe_predicate_eval()
  • lint_catalog()
→ Findings + coverage
5

Interpret

Interpreted agents.orchestrator

Two agents run at the same time. The commentary agent takes the findings needing engineering judgement, in batches, and writes what each measurement implies. The summary agent sees the whole part at once and writes the opening narrative — headline, assessment, ranked risks with recommendations.

Why batched One request covering many findings lets the model see that eight faces failed the same rule and describe the pattern. The summary agent groups by rule first, so one rule failing on eight faces takes one slot rather than crowding out a different problem.
What runs
  • agents/orchestrator.py · llm.py
  • enrich_review_findings()
  • _request_commentary()
  • generate_executive_summary()
  • _rank_findings_for_summary()
  • LLMClient.complete_json()
→ commentary on findings + summary
6

Validate

Computed orchestrator.validate()

Audits the report against itself: a fail verdict with no measurement behind it, a finding pointing at a face that does not exist, a skipped rule with no reason given, and two rules in the same category disagreeing about the same face.

Why it matters This catches the system being confidently wrong rather than merely incomplete. A contradiction means rule scoping has broken somewhere, and it belongs in the report rather than in the client's inbox.
What runs
  • agents/orchestrator.py
  • validate()
  • _find_contradictions()
  • + ingest warnings
→ validation issues
7

Report

Computed main.py · /api/analyze · /api/report

Assembles the response, saves a versioned record so this run can be compared against a later revision of the same part, and returns everything the interface needs. The same stored record also renders on demand as a standalone HTML or PDF report.

Why it matters Persisting each run is what makes the rework story possible: review revision A, let the design engineer fix it, then show exactly which findings closed in revision B. Because the report reads that record rather than re-running the part, it can be reopened at any time at no cost.

05
Before any rule runs

The part says how it was meant to be made

Choosing the process by hand is the one step where a user can be silently, expensively wrong. Pick "machining" for a moulded housing and every draft rule is skipped: the report comes back clean and says nothing about the defect that mattered most.

Computed

What separates the processes

A moulded part and a machined part do not look alike, and the difference is measurable.

  • Draft — a moulded wall is tapered so the tool can open; a machined wall is square, because that is what a cutter leaves
  • Wall thickness and its spread — moulded parts are designed to a nominal wall, machined ones are whatever the pocket left
  • Corner radii — internal corners sharing one radius are the signature of a single cutter
  • Gauge and proportion — sheet metal is one thickness, far thinner than anything else about the part
  • Solid count — more than one solid is an assembly
Interpreted

The reading

A language model turns the scores into two or three sentences an engineer would accept — quoting the measurements, not describing them. It explains the conclusion; it cannot change it.

  • Which process the part reads as, and on what evidence
  • What would settle a close call
  • What in the reading to be careful about

Every candidate is analysed, not just the winner. A part that could be machined or pressed gets both sections, each labelled with how it was read. Being wrong then costs a section nobody reads, rather than a defect nobody sees. Two things are stated rather than guessed around: a physical impossibility rules a process out outright (forming cannot change the gauge of the sheet it started from), and a process recognised only by what it is compatible with is offered as a possibility, never as a conclusion.

The limit, stated plainly. A STEP file carries no material. Injection moulding and die casting are the same shape, so geometry cannot tell them apart at all — when both score highly the report says so and analyses both, rather than picking one.

06
Reading the output

Every finding lands in one of five states

The distinction between "this failed" and "this was never checked" is the difference between a report you can act on and one you have to audit.

StatusMeansDecided by
COMPLIANT Measured, and it satisfies the rule. Geometry
NON-COMPLIANT Measured, and it violates the rule. Geometry
NEEDS_REVIEW Needs engineering judgement — a genuinely qualitative rule, or advisory guidance the part falls outside. The only status the language model ever comments on. Geometry flags, model explains
NOT_EVALUATED The rule did not run, and says why: wrong material, no extractor for the metric, no face carrying the feature, or a catalogue entry the linter found untrustworthy. Rule scoping
ERROR Evaluation was attempted and failed. Engine

Coverage is stated, not implied. On a typical part around 19 of 70 injection-moulding rules produce a verdict; the rest need feature recognition, process inputs, or a corrected catalogue entry. The interface shows that count and the executive summary repeats it in words. A report that looks complete when it tested a third of the catalogue is worse than one that admits the gap.

The model itself is the third output. Every finding names a face, and a face number means nothing to a person reading a table. The part is tessellated during the analysis and every triangle carries the same face number the rules used, so the view can paint each face by its worst finding — red for failed, amber for review, green for passed, grey where no rule reached — and a click on a wall narrows the table to what is wrong with that wall. It costs no extra time: the meshing runs while the model requests are in flight.

The assessment, in words

The model-written summary and its ranked risks open the document, so the first thing a reader meets is what the part's problem actually is — not a table they have to interpret.

Measurement against its limit

For the rules carrying real numbers, every measured face is plotted against the band the rule allows. A wall at 0.82 mm against a 1.0 mm floor reads instantly as marginal; one at 0.31 mm does not.

One row per problem, not per face

A rule failing on thirty faces is one finding worth reading once, with the locations listed. The interface keeps the per-face detail; the document collapses it.

What was not evaluated, and why

The coverage bar and the not-evaluated section carry into the PDF. Nothing about the document lets a reader mistake a partial check for a clean bill of health.

One template, two renderers. The browser view and the PDF are the same markup — the charts are SVG drawn on the server rather than by a JavaScript charting library, so they survive the trip into the PDF unchanged. There is one place to change the design, and the two outputs cannot drift apart. Reports render from the stored run rather than re-analysing, so opening one months later is instant and costs nothing — including no further model calls.

08
Confidence

How we know the measurements are right

Geometry cannot be checked by eye — a wall thickness of 1.87 mm looks equally plausible whether it is right or wrong. Two independent lines of evidence.

Parts with known answers

Test parts are generated from primitives with exact dimensions — a 2 mm shelled box, a wall drafted by exactly 2.862°, a plate with a Ø5 mm hole, a block with a cross-bore that cannot be moulded. Each measurement is asserted against the number the part was built with, so a regression fails here rather than silently changing every customer report.

Real CAD from a public benchmark

The full NIST MBE PMI validation set — 33 STEP files of real machined test artifacts, in AP203 and AP242, mixing millimetre and inch, and deliberately containing syntax errors. All 33 process without failure, and every face of every well-formed part is measured.

The claim worth making about the process reading is a safety one, and it is measured. Across all 33 NIST parts — machined artifacts, every one — the reading named machining first on 21. On the other 12 it did not, and on 11 of those the machining rules were checked anyway, because every candidate above the threshold is analysed. One part fell outside: a six-face reference body drafted throughout, where machining genuinely does not fit. So a misread costs a section nobody reads rather than a defect nobody sees, which is the property the whole design is built around.

Both are needed and they catch different things. Synthetic parts prove the arithmetic is right; real files prove the assumptions behind the arithmetic are right. Unit handling, for instance, is confirmed by an inch-declared part reporting Ø4.763 mm and Ø7.938 mm holes — exactly 3/16″ and 5/16″, standard drill sizes, correctly converted.

What it is built on

Where each piece runs, and what it costs

LayerTechnologyNotes
Geometry OpenCascade via pythonocc-core Runs locally. The same kernel behind several commercial CAD tools.
Feature naming Python, from the measured geometry Names every face by shape, size and position. Deterministic — no model involved, because a wrong name is worse than a number.
Process reading Weighted geometric tests + DeepSeek V4 Flash Scores every family from measured signals; the model writes the rationale but cannot change which sets are checked.
Rules Python + JSON catalogue 249 rules across 10 process families, linted at load and executed one family at a time so coverage stays per-family.
Interpretation DeepSeek V4 Flash via OpenRouter One request per rule needing judgement — not per finding — batched and run concurrently. Usually under a dozen. Optional: with no key the report still carries every verdict and every feature name.
API FastAPI + SQLite Each run is versioned so revisions can be compared.
Interface React + Material UI Findings table, coverage dashboard, revision comparison.
3D view OpenCascade tessellation + three.js Face numbering shared with the analysis, so a click resolves back to that face's findings.
Report Jinja2 + WeasyPrint, charts as server-drawn SVG One template renders both the browser view and the PDF, from the stored run rather than a re-analysis.

Only measurements leave the machine. The model receives rule names, measured values and part-level metadata such as overall size and nominal wall thickness. The STEP file and its geometry are never uploaded. If design data is restricted, that distinction is a property of this design rather than of the provider — it holds if the model is later swapped or moved in-house.

10
Being straight about it

What this does not yet do

A demo that oversells is harder to recover from than one that is candid.

Checking every candidate costs time

A single-family run takes around 50 seconds; checking every candidate for a large ambiguous part takes 60 to 90. Almost all of it is the commentary requests — measuring a 637-face part takes under three seconds. Those requests scale with the number of rules needing judgement rather than the number of findings, which is what keeps a 306-face part checked against five catalogues to a minute and a half rather than ten. Worth knowing before a live demo.

The process reading is evidence, not certification

It scores what the geometry is consistent with. It cannot see the material, the volume, the tooling budget or the supplier — all of which really decide the process. Treat it as the shortlist a colleague would give you after a minute with the model, not as a routing decision.

Coverage is partial, by roughly two thirds

Around 19 of 70 injection-moulding rules produce a verdict on a simple part. The rest need feature recognition, process inputs such as surface finish, or corrected catalogue entries. This is visible in the report rather than hidden.

Features are named by shape, not by purpose

A finding now says "Ø5.94 mm hole, upper front right" rather than "face 214", and the 3D view shows you which one that is. What it will not say is "the mounting hole" or "the boss near the parting line", because nothing here measures purpose. That restraint is deliberate — a name that sends an engineer to the wrong feature costs more than a name that tells them nothing — but it does mean the report describes the part rather than understanding it.

Thickness is a ray measurement

On curved or tapered walls it returns a chord at or above the true perpendicular thickness. Production tools use an inscribed-sphere method, which is more accurate and more expensive.

The catalogue has known bad entries

Some rules were damaged converting the source spreadsheet — a numeric range read as a date, thresholds that lost the dimension they were a multiple of. These are detected at load and refused rather than allowed to produce a confident wrong answer, but the source data still needs fixing.
